## Whether Neon Free is sustainable

Current documentation lists **100 CU-hours/project/month**, **1 GB/project storage** and **5 GB/project public transfer**. Account usage, other branches, and actual billed storage are not available through the worker's SQL credentials. The owner must confirm the existing project is Free and has enough remaining allowance; the source's older 0.5 GB figures are superseded by the current published plan, not by an account inspection.

Continuous 15–30-second lease/heartbeat queries prevent inactivity. The new supervisor starts its hard wall before opening SQL, runs preflight and the unchanged worker inside it, drains/terminates within the wall, closes every SQL client, and then uses only local timers/files. The five-minute Neon suspension tail is included in the model. SQL counts and application reservations are **not billed CU-hours**. Actual suspension must be checked in the Neon console without a continuously polling SQL client.

Each selected window reserves one modeled CU-hour at the conservative 2 CU assumption; for a partial month, allow two per remaining day plus other project usage. The default 31-day worker envelope is `62 windows × (25 + 5) minutes × CU / 60`. Its worst Free-autoscaling assumption is 2 CU: 62 CU-hours, leaving 38 of the published 100 for web activity, other computes and unexpected wakeups. A durable **70 modeled CU-hour** worker reservation guard adds a conservative stop; it is not an account billing meter. Failed/interrupted reservations are not refunded. Frequent restarts, external SQL health checks, logical replication, development branches or heavy web use can invalidate the idle assumption and exceed Free even though the worker itself sleeps.

The frontend's unattended one-minute server refresh was removed. Navigation, browser reload and completed actions still fetch data; freshness labels keep advancing on the client without SQL. Main navigation also avoids speculative page prefetch. This does not turn old observations into fresh data. Do not keep database consoles/SQL monitors issuing repeated queries during planned idle.

## Start, stop, health and recovery

Render starts the container automatically after the approved deployment. The supervisor stays running during sleep; it does not hold a database connection or poll SQL to decide when to wake. Its local health file is updated without database writes. An allocation and conservative debit persist in Neon before work begins, so restarting the container does not obtain another window early. There is no burst catch-up of missed windows.

To stop: suspend the worker in Render. `SIGTERM` stops new provider calls, drains active work and has a 75-second forced-shutdown fallback; the prepared platform grace is 90 seconds. To resume, start one instance of the same verified revision. A process may deliberately wait until its stored next wake time; do not erase that setting or refund a reservation to make it run sooner.

Container-local check: `node --import tsx scripts/worker-health.ts`. It checks the local process/timestamp/planned sleep without waking Neon, and reports unhealthy for stored failure state. Render may not execute Docker HEALTHCHECK for background workers; platform failure notifications, logs and first-cycle inspection are still necessary. A healthy sleeping supervisor is not fresh market data. Preflight/connection failures are visible in logs and local health; fix the cause and preserve the cooldown, or suspend the service.

Locally, use `npm run worker:status` or `npm run collection:status` with the existing local secret file. In the Render Shell, where secrets are injected as environment variables, use `node --import tsx scripts/worker-status.ts` and `node --import tsx scripts/collection-status.ts` instead. These inspect duty state, leases, budgets, source ages and unsupported networks. Do not schedule SQL monitoring every minute or enable `FLOWNIX_WORKER_HEALTH_ENABLED` hourly for this mode: it wakes Neon and the continuous-heartbeat check intentionally fails during sleep. In-app alerts retain their evidence; optional external delivery needs explicit configuration/permission.

Provider budgets are reserved before dispatch. Exhaustion defers the affected provider until reset, without refunding failed/uncertain requests. Other eligible jobs can continue within the window. Monthly modeled Neon budget exhaustion sleeps until the next UTC month; it does not upgrade anything. Storage/configuration guard exit 78 requires a reviewed fix. If the Free account itself denies requests, collection stops/retries and existing evidence remains; inspect the dashboard rather than changing billing.

Interrupted jobs retain committed checkpoints and recover after lease expiry in a later allowed window. Solana gaps remain gaps. Unexpected repeated restarts consume unmodeled wakeups: suspend a looping service rather than allowing it to keep Neon awake.

Rollback: suspend the worker first, retain the existing database and all additive tables/settings/ledgers, then select the last verified **duty-aware** worker revision. Do not run the older continuous image against Neon Free as a rollback: it can exceed the budget. If no duty-aware previous image is available, remain suspended while the defect is corrected. Vercel/frontend rollback is separate and must not reset evidence.
